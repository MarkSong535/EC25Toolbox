# Proton Drive archives

Scope: this gateway's SMS/call email records, message database, outgoing requests,
access logs and activity logs. This does **not** export your entire Proton Mail
mailbox. `.eml` files are reconstructed from recorded events, with the sender name
and configured address; original SMTP transport headers are not available.

Archive files are deliberately **not encrypted or password-protected by this
application**: `.tar.gz` is compression only, containing ordinary `.eml`, JSONL,
JSON and SQLite files. After downloading through Proton Drive, they open without
GPG, a separate decryption key or an archive password. Proton Drive's own automatic
end-to-end encryption still applies during storage and cannot be disabled here.
The GPG credential store discussed below protects only the Proton login session;
it never encrypts the archive or log contents.

The official Proton Drive CLI 0.8.0 ARM64 binary is installed at
`/usr/local/bin/proton-drive`. Its SHA-512 was verified against
[Proton's release page](https://proton.me/download/drive/cli/index.html).
It supports browser-based login and Linux password-store credentials; see the
[official CLI README](https://github.com/ProtonDriveApps/sdk/blob/main/cli/README.md).

## Install the pinned ARM64 CLI

On an ARM64 Debian/Raspberry Pi OS host, download only the official binary and
verify the pinned SHA-512 before installation. Run this block in a shell on the Pi:

```sh
(
set -eu
test "$(uname -m)" = aarch64
sudo apt install -y curl ca-certificates gnupg pass
proton_stage=$(mktemp -d /tmp/ec25-proton-cli-XXXXXXXX)
curl --fail --location --proto '=https' --tlsv1.2 \
  https://proton.me/download/drive/cli/0.8.0/linux-arm64/proton-drive \
  -o "$proton_stage/proton-drive"
printf '%s  %s\n' \
  27a1aec1d2095fd4a1a81e1d47cd1f9fd4901bd579ffe50342d15e2e52078d6e8b2dddcf58a4a386438dc7562017778be26c1ba62399f901ae82c7430e2140a3 \
  "$proton_stage/proton-drive" | sha512sum -c -
sudo install -m 0755 "$proton_stage/proton-drive" /usr/local/bin/proton-drive
/usr/local/bin/proton-drive version
rm -- "$proton_stage/proton-drive"
rmdir -- "$proton_stage"
)
```

Use the matching release artifact/checksum for another architecture; do not
substitute an unverified binary. These installation commands do not log in or
enable any scheduled upload. The application archive runner pins its credential
backend to `pass` and its CLI log level to `ERROR`.

## Authentication requirement

The Pi has no desktop secret-service session. The CLI works using
`PROTON_DRIVE_CREDENTIALS_STORE=pass` from the service account's home directory.
Authentication is per Unix account. A folder listing from your administrator
account does not prove the `ec25toolbox` service can upload. Check its login
explicitly; this document makes no claim about current account/session state.

To use a passphrase-protected key, run these interactively in **your own SSH
terminal**, not chat (enter the passphrase only into GPG's prompt):

```sh
sudo -Hu ec25toolbox bash
cd /var/lib/ec25toolbox
export GPG_TTY=$(tty)
gpg --full-generate-key
# Choose an encryption-capable key and a strong passphrase.
gpg --list-keys --with-colons
pass init YOUR_KEY_FINGERPRINT
PROTON_DRIVE_CREDENTIALS_STORE=pass proton-drive auth login
# Follow the Proton browser sign-in URL. Keep the terminal running.
PROTON_DRIVE_CREDENTIALS_STORE=pass proton-drive filesystem create-folder /my-files RPI-SMS
exit
```

For scheduled work the credential store must be unlockable in that service
session. A passphrase-protected GPG key may require unlocking again after its
agent cache expires or after reboot; the scheduled job fails safely while locked.
This setup does not pretend to solve unattended unlocking without a storage
decision. Do not put account passwords or GPG passphrases into config.toml.

### Optional unattended key (explicit operator security decision)

A dedicated passphrase-free GPG key avoids cache-expiry/reboot unlock prompts,
but anyone obtaining that key and password store can decrypt the saved Proton
session. Filesystem permissions and host security then carry that protection.
Do not remove the passphrase from a personal key or silently migrate an existing
store. Proton may still expire/revoke login independently of GPG.

For a **new** service-only store, after accepting that tradeoff, an operator can
use this instead of `gpg --full-generate-key` in the service-account shell:

```sh
gpg --batch --pinentry-mode loopback --passphrase '' \
  --quick-generate-key 'EC25 Proton Archive' rsa3072 encr 0
gpg --list-keys --with-fingerprint 'EC25 Proton Archive'
pass init YOUR_NEW_KEY_FINGERPRINT
```

Do not run `pass init` against an existing populated store without a protected
backup and a deliberate re-encryption plan. No key is generated by our installers.
GnuPG documents [unprotected key generation](https://gnupg.org/documentation/manuals/gnupg/Agent-GENKEY.html).

### Inspect the actual credential key without printing credentials

```sh
sudo -Hu ec25toolbox bash
cd /var/lib/ec25toolbox
find .password-store -name .gpg-id -print -exec cat {} \;
gpg --batch --no-autostart --pinentry-mode error --keyid-format long \
  --list-only --decrypt \
  .password-store/ch.proton.drive/drive-sdk-cli/auth-session.gpg
gpg --list-secret-keys --keyid-format long --with-fingerprint --with-subkey-fingerprint
PROTON_DRIVE_CREDENTIALS_STORE=pass PROTON_DRIVE_LOG_LEVEL=ERROR \
  proton-drive filesystem list /my-files/RPI-SMS
exit
```

Subfolder `.gpg-id` entries override parent selection; the encrypted session's
recipient metadata identifies the actual encryption key, possibly a subkey.
Never paste `pass show` output into chat/issues. A successful folder listing
proves access, not upload integrity; the next section checks the complete path.

## Central settings and scheduling

```toml
[archive]
enabled = true
remote_path = "/my-files/RPI-SMS"
binary = "/usr/local/bin/proton-drive"
interval_hours = 24
max_archive_mb = 64
```

The archive service/timer is installed but intentionally not enabled until
credentials are ready. The timer wakes hourly; the central interval controls
when a new archive is due. After completing login and an actual successful run:

```sh
sudo systemctl start ec25toolbox-archive
sudo journalctl -u ec25toolbox-archive -n 20 --no-pager
sudo systemctl enable --now ec25toolbox-archive.timer
```

Before enabling the timer, require the log message `Uploaded and download-verified`
and a new receipt in the portal. `Archive not due` and `Archiving disabled` are
not new uploads. To force a run while `[archive].enabled=true`:

```sh
sudo -Hu ec25toolbox sh -c 'cd /var/lib/ec25toolbox && \
  PYTHONPATH=/opt/ec25toolbox /opt/ec25toolbox/venv/bin/python \
  -m ec25toolbox_linux.archive --config /etc/ec25toolbox/config.toml --force'
```

Each run takes a consistent SQLite snapshot and creates a compressed `.tar.gz`
with the database, JSONL records, `.eml` representations and a SHA-256 manifest.
It uploads a unique filename using conflict-skip, downloads that exact file to a
temporary verification directory and compares its SHA-256. Only then does it
record a verified receipt. This is **upload-only archiving**, not a two-way sync:
the verification download is a one-file integrity check, not a local cloud mirror.
It never replaces/deletes remote content, empties trash, or deletes the live DB.

Temporary exports are cleaned after the attempt; failed attempts preserve all
original data in the live database. Verified archive copies do not accumulate
locally. The small active database remains so the portal can display all retained
history. Its growth is not pruned automatically. A size limit and free-space check
stop oversized backups rather than risking a full disk. The CLI also maintains
its own credential/cache data; this is not a mirror of your Drive files.

## Download and recover

Use the portal's Archives view for the filename, checksum and verified time.
Download that file from the `RPI-SMS` folder in [Proton Drive](https://drive.proton.me).
Proton decrypts it when downloading. Verify against the recorded checksum before
restoring. Archive receipts also live in SQLite's `portal_archives` table.

Alternatively, run the checksum-verifying recovery command as the service user:

```sh
sudo -Hu ec25toolbox bash
cd /var/lib/ec25toolbox
PYTHONPATH=/opt/ec25toolbox /opt/ec25toolbox/venv/bin/python -m ec25toolbox_linux.archive \
  --recover sms-TIMESTAMP-IDENTIFIER.tar.gz \
  --sha256 SHA256_FROM_RECEIPT --output /var/lib/ec25toolbox/recovered
exit
```

It refuses to overwrite an existing destination. Recovery downloads an archive;
it does **not** overwrite the live database or merge records automatically.
Extract into a fresh directory, inspect `manifest.json`, and read `.eml`/JSONL
files directly. To restore the database after a disaster, stop the gateway,
preserve the current DB plus WAL/SHM, verify the snapshot using SQLite
`PRAGMA integrity_check`, and restore ownership to `ec25toolbox` before starting.
Do not roll back a live database casually: newer SMS and delivery/deduplication
state would be lost and old sends could be reintroduced. No secrets/configuration
or GPG private key is included in the archive; back those up separately and securely.
